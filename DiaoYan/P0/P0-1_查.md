### 问题 1:`_htmlShell()` 的准确起止行号与返回形式

- 函数签名:第 3065 行 `String _htmlShell() {`(`file:lib/presentation/screens/chat/webview_chat_stage.dart:3065`)。
- 字符串体:第 3066 行 `return '''` 开始,第 4581 行 `''';` 结束(三单引号多行原始字符串,非 raw,可插值)。
- 函数闭括号:第 4582 行 `}`;所在 State 类闭括号第 4583 行 `}`。

### 问题 2:shell 内的动态插值点全清单(核心难点)

用三种手段交叉核对,确认 shell 里 Dart 插值点**恰好 3 处**:

| # | 行号 | 插值表达式 | 注入的是什么 |
|---|---|---|---|
| 1 | 3101 | `${_colorToCss(ref.watch(quoteColorStateProvider).primaryA)}` | **运行期主题色**(quote-q 颜色,读 riverpod `quoteColorStateProvider`,转成 CSS 十六进制) |
| 2 | 3102 | `${_colorToCss(ref.watch(quoteColorStateProvider).primaryB)}` | **运行期主题色**(quote-p 颜色,同上) |
| 3 | 3404 | `$kChatBridgeJs` | **静态常量**(`chat_bridge_js.dart:23` 的 `const String kChatBridgeJs = r'''...'''`,整段桥 JS 源码,raw 字符串、内部无插值) |

**我是怎么区分三类 `$` 的:**

1. 反引号(JS 模板字符串 `${}`):先 grep 整个 shell 范围内含 `` ` `` 的行 → **0 行**。所以 shell 里没有任何 JS 模板字符串,不存在"JS 自己的 `${}`"干扰项。
2. jQuery 的 `$`:第 3559 行 `html.indexOf("\$(")>=0`。我抓了该行原始字节,`\$` 是 `5C 24`(反斜杠+美元),这是 **Dart 里被转义的美元号**,编译后变回字面 `$`;它后面跟着 `(` 而非字母/下划线,且夹在 `"..."` 字符串里,是 jQuery 检测逻辑,不是插值。
3. 真正的 Dart 插值:把 shell 范围内(3066–4581)所有含 `$` 或 `` ` `` 的行列出,只剩 3101、3102、3404 三行;其中 3101/3102 是 `${expr}`,3404 是 `$ident`,都符合 Dart 插值语法,且前面没有反斜杠。

字节级核对证据(我对转义疑点做了 hex dump,部分节选):

```
=== line 3559 ===
```

大白话:抽离时**只要处理这 3 个洞**,漏掉任何一处,抽出来的 HTML 要么颜色不对(3101/3102),要么整个桥直接消失、WebView 无法和 Flutter 通信(3404)。这是全 P0 最大的坑,第 2 步的脚本会特别盯着它们。

### 问题 4:shell 怎么送进 WebView、在哪个生命周期

- 送法:`webview_chat_stage.dart:576-581`:
  ```dart
  initialData: InAppWebViewInitialData(
    data: _htmlShell(),
    mimeType: 'text/html',
    encoding: 'utf-8',
    baseUrl: WebUri('about:blank'),
  ),
  ```
  即用 `_htmlShell()` 的返回值直接作为 HTML 文本,通过 `InAppWebViewInitialData` 喂给 WebView(`data:` 形式,baseUrl 是 `about:blank`)。
- 生命周期:在 `build` 树里,`_webViewMounted == true` 时才创建 `InAppWebView`(第 559-560 行),此时 `initialData` 同步取值一次。**这是 WebView 创建时的同步初始化,不是 load 后注入。**
- 补充(shell 之外、但同属页面):`onLoadStop`(637 行)之后才做 `_injectCompatLibs` / `_injectMacroValues` / `_injectEngineFacade` / `_injectMvuBundle` / `_injectEjsStub` / `_injectEjsBundle`,最后 `evaluateJavascript('if(window.createEngineRoom)...')` 点火建引擎房。

大白话:shell 是 WebView 睁开眼那一刻**一次性地**喂进去的"初始页面";而 jquery/lodash/MVU/EJS 这些是在页面加载完成后,再通过 `evaluateJavascript` 补进去的。两条注入路径不同步,这决定了下文"抽离后时序怎么保证"的讨论基础。

### 问题 5:`assets/libs/*.js` 现在怎么读、怎么注入?抽离能否照抄?

现在(以 jquery 为例,`webview_chat_stage.dart:149-165` + `:200-215`):

1. **读**:`_loadCompatLibs()` 里 `await rootBundle.loadString('assets/libs/jquery.min.js')`(152 行),`utf8.encode` 后 `base64Encode`,存进 `static String? _jqueryB64`(156 行)。
2. **注入**:页面 `onLoadStop` 时 `_injectCompatLibs` 用 `evaluateJavascript` 把 `window.__KIRA_LIBS = { jquery: "<b64>", ... }` 写进外层 window(204-211 行),供 shell 内的 `injectBridge` / `createEngineRoom` 用 `decodeB64Utf8` 还原成 JS 源再内联进 iframe。
3. MVU/EJS 同理(loadString → 静态缓存 → onLoadStop 时 evaluateJavascript 注入 window)。

**抽离能不能照抄:不能直接照抄"这条"路径,要点是——** 这条路径是"异步 loadString + 运行时 evaluateJavascript 注入",而 shell 现在走的是"**同步**返回一个已插值完成的字符串"。两者时序不同:shell 必须在 `InAppWebView` 构造前拿到完整 HTML。若要抽成 asset 且仍走 `loadString`,就必须先 `await` 读完 asset 再构造 WebView(即把 `_htmlShell()` 从同步变成异步),这一步属于第 3 步"诊"的判断,本步只记录事实:项目里**有** `rootBundle.loadString` 成熟先例,但**没有**"把初始 HTML 从 asset 读出来的"先例(现有的 `assets/live2d_web/index.html` 是给 live2d 用的,不走聊天 stage)。

大白话:现有代码里"从 assets 读文件"的 API 成熟且重复用了 8 次,但那是"加载后补刀"的用法;而 shell 是"出生时就要有"的初始页,抽离时要解决"怎么在 WebView 出生前把文件读完"这个新的时序问题。这是整件事真正的技术难点,不是 API 有没有的问题。

### 问题 6:`#root`(3354)与 `#__engineRoomHost`(3355)的父子/兄弟关系(命令确认)

```powershell
Select-String -Path "lib\presentation\screens\chat\webview_chat_stage.dart" -Pattern 'id="root"|id="__engineRoomHost"|<body>|</body>' | ForEach-Object { "$($_.LineNumber): $($_.Line.Trim())" }
```

```
3353: <body>
3354: <div id="root"></div>
3355: <div id="__engineRoomHost" style="display:none;width:0;height:0;overflow:hidden;"></div>
...（3796/4445/4446/4480 的 </body> 都是 JS 字符串里的字面量,与静态骨架无关）
```

结论:**`#root` 与 `#__engineRoomHost` 是兄弟关系**(都是 `<body>`(3353–4579)的直接子元素,3354、3355 相邻),不是父子。`#__engineRoomHost` 在 `#root` **之外**(`style="display:none;width:0;height:0;overflow:hidden"` 隐藏容器,专门用来装引擎房 iframe)。

大白话:引擎房 iframe(`createEngineRoom` 创建的)挂在 `#root` 外面的一个隐藏小盒子里。这跟报告 13 A5 的结论一致——引擎房不在消息区 DOM 里。抽离 shell 时只要这两个 div 的相对位置/顺序不变,引擎房就不会被误伤(第 3 步会继续盯这条)。
