# P0-3 诊 — 抽离可行性与风险诊断

> 性质:只诊断、不提改动清单(清单留给 P0-4)。本步零代码改动。
> 依据:P0-1(现状)与 P0-2(已验证 `node --check` 路线可行)+ 本步对 `backup/p1-failed`、`backup/c1-alpha-failed` 两个失败分支做了实证检查。

---

## 一、必答问题

### 问题 1:抽离可行吗?

**结论:有条件可行。**

依据(全部来自已执行的命令,非推测):
1. 项目已有成熟先例:8 处 `rootBundle.loadString('assets/libs/*.js')`(P0-1 问题 5 的输出),读资产这条路本身没问题。
2. `pubspec.yaml:102` 已有 `- assets/` 整目录声明,新建任何 `assets/xxx` 文件**不用改 pubspec**(P0-1 的 1-5 输出)。
3. P0-2 已证明 `_htmlShell` 的 JS 能被完整还原成 `.js` 并通过 `node --check`(exit 0),即"机器检查 JS 语法"这条路走得通。
4. **唯一真正的障碍**:`_htmlShell()` 现在是**同步**返回字符串、被 `InAppWebViewInitialData`(576 行)同步消费;而 `rootBundle.loadString` 是**异步**。要把 shell 变成 asset,必须把"读文件"提前到 WebView 构造之前(项目里 `_webViewMounted` 这个"延迟挂载"机制 88 行,天生提供了一个先读后挂的 gate,详见问题 2/5)。

所以不是"能不能抽",而是"抽的时候必须顺手把同步改异步、且不改坏引擎房时序"——这是条件,不是障碍本身。

大白话:能抽。工具、先例、入口都齐了;唯一要动的是『把读文件提前到 WebView 出生前』这一步时序,动作不大但必须做对。

### 问题 2:动态插值怎么解决?哪个最麻烦?

shell 内共 **3 个插值点**(P0-1 问题 2 已全文核对),逐个方案:

| 插值(内容锚点) | 性质 | 方案 | 难度 |
|---|---|---|---|
| `$kChatBridgeJs`(3404 行) | **静态常量**(`chat_bridge_js.dart` 的 `const`,4977 字符,raw 字符串无插值) | 直接内联进 asset(桥 JS 随壳子一起进 asset,`node --check` 还能顺带查它);或保留占位 `__KIRA_CHAT_BRIDGE__` 由 Dart `replaceAll` 填回。**首选:内联** | 低 |
| `${_colorToCss(ref.watch(quoteColorStateProvider).primaryA)}`(3101 行) | **运行期主题色**(读 riverpod) | asset 里放占位 `__KIRA_QUOTE_Q_COLOR__`,Dart 侧 loadString 后 `replaceAll` 成 `_colorToCss(...)`;或干脆靠 CSS 已有 fallback `var(--quote-q-color, #FFA726)` + onLoadStop 用 `evaluateJavascript` 调 `documentElement.style.setProperty('--quote-q-color', ...)`。**首选:replaceAll**(与现在 build 期取值行为最接近) | 中 |
| `${_colorToCss(ref.watch(quoteColorStateProvider).primaryB)}`(3102 行) | **运行期主题色** | 同上,`__KIRA_QUOTE_P_COLOR__` | 中 |

**哪个最麻烦?** 三个插值本身都不难;真正麻烦的是**第 4 个"插值"之外的障碍**——`initialData` 是同步的、`rootBundle` 是异步的,这个时序缺口比任何插值都关键。若必须在 3 个插值里选一个最麻烦:**两处颜色**是仅有的"真正运行时值",不能烙进静态文件,必须留占位在 Dart 侧填——一旦漏填,配色的主题跟随就静默失效(最不易察觉,因为页面不报错、只是颜色不对)。

大白话:桥是死的(塞进去就行),颜色是活的(得留洞、运行时填)。最容易翻车的不是它们,而是"文件还没读完、WebView 就想出生"的先后顺序;三个洞里若必须点名,颜色最阴——它错了不报错、只变色。

### 问题 3:热重载行为会变吗?

**大部分「未验证」,不猜。**

可分两层说清楚:
- **"现在改 shell 要重启 app"这个前提**:这是本指令给定的前提,我**未能在本机验证**(我跑不了 app)。从代码看,`initialData: _htmlShell()`(576 行)只在 `InAppWebView` 构造时取值一次,且用了 `GlobalKey`,老 WebView 的 native 状态是否被热重载保留、`_webViewMounted` 是否重新走挂载,我无法确认。
- **"抽成 asset 后 rootBundle 在 debug 下的行为"**:按 Flutter 文档,asset 变更需要**重新构建 asset bundle**(即热重启/重启),普通热重载**不会**重载 asset 文件。但这是**据文档、未在本机验证**。

诚实结论:抽离后"改 asset 也要热重启"的概率很高,和"现在改 Dart 字符串要重启"基本打平;P0 抽离**不指望**靠它换来热重载体验提升,图的是**提交前能机器验 JS 语法**。这一点我不会替你真机下结论。

大白话:别指望抽离后就能热重载着调 JS——asset 大概率要热重启才生效,和现在差不多。抽离真正买到的是『提交前机器把关』,不是『改起来更快』。

### 问题 4:打包/发布风险

1. **assets 声明**:`pubspec.yaml:102` 已有 `- assets/` 整目录,新增 asset 文件**无需改 pubspec**。低风险。
2. **release 构建**:asset 走与现有 `assets/libs/*.js`(8 处 `rootBundle.loadString` 已在 release 正常工作的先例)完全相同的打包链,不引入新机制。低风险。
3. **Android/iOS 差异**:`rootBundle` 是平台无关抽象,本项目已跨平台用 8 处。低风险。
4. **UTF-8 BOM**:源 `webview_chat_stage.dart` 本身带 BOM(P0-2 已实证)。风险在于**新建的 asset 文件**若被编辑器/工具链写成带 BOM,`rootBundle.loadString` 返回的字符串头部会多一个 `U+FEFF`。HTML 解析器按规范会忽略开头 BOM(风险低),但**不该赌**——落地时 asset 文件一律写**无 BOM** 的 UTF-8,并作为一条明确的施工约束写进 P0-4。这是唯一需要主动防的编码坑。

大白话:打包几乎无风险(和现有 js 资产同一套路),唯一要盯的是"新文件别带 BOM、别带 CRLF 之外的意外编码"。

### 问题 5:引擎房风险

结论:**不危及,前提是把 JS 文本保持字节级一致。**

证据链(全部实地核过):
- `#root`(3354)与 `#__engineRoomHost`(3355)是**兄弟**,都直接挂在 `<body>` 下(P0-1 问题 6 命令输出),`#__engineRoomHost` 在 `#root` 之外、是个 `display:none` 隐藏容器——与报告 13 A5 一致。
- `createEngineRoom`(shell 内 JS)在**运行时自己拼**引擎房 iframe 的 `doc` 字符串(4445 行起),不读任何外部文件,然后 `host.appendChild(frame)` 挂进 `#__engineRoomHost`。它跟"shell 是字符串还是 asset"无关。
- Dart 侧的 `_injectCompatLibs / _injectMacroValues / _injectEngineFacade / _injectMvuBundle / _injectEjsStub / _injectEjsBundle` 与 `onLoadStop` 里的 `window.createEngineRoom()` 点火(637–645 行),也跟 shell 来源无关。

**真正的风险**正是 P0-3 新发现的:只要 shell 的 JS **任何一句**语法错,整个主 `<script>` 块不会被浏览器解析,`createEngineRoom`/`resetEngineRoom`/`setMessages`/`appendToken` 等**全部函数一起死**,引擎房当然也建不起来(见问题 6 与问题 8 的实证)。所以保护引擎房的方式不是"小心手改",而是"用 node --check 在提交前把语法锁死 + 用内容等价 diff 保证抽离前后逐字一致"。

大白话:引擎房挂在 `#root` 外面的隐藏盒子里,跟壳子怎么来没直接关系;但壳子里 JS 只要一处写错,整个脚本块都会哑火、引擎房跟着塌。所以抽离时真正要保的是『JS 文本一个字都不差』。

### 问题 6:失败的样子与第一时间发现

如果抽离没做对,最可能的症状(按严重度):

| 症状 | 根因 | 第一时间怎么发现 |
|---|---|---|
| 整页白屏 / 空 WebView | asset 读失败或读到空、`_webViewMounted` gate 没等到读 | 真机看是否白屏;日志看有没有 `[bridge]`/`[TH中转]` |
| 桥不可用:发消息/回指令全没反应 | `$kChatBridgeJs` 没填进去,`sendToFlutter`/`registerBridgeHandler` 未定义 | 真机 logcat 看 `no JS handler` / `[dispatch错误]`;或直接看 shell 产物里是否残留 `$kChatBridgeJs` |
| 主题色失效(能跑但不跟随主题) | 两处颜色占位没被替换 | 视觉:引号颜色退回 fallback `#FFA726`/`#29B6F6`;或在产物里 grep `__KIRA_QUOTE_` |
| **整页 JS 全死**(引擎房、渲染、流式全挂) | 三引号转义写错导致 JS 语法错(见问题 8 的 `'\n'` 案例) | **`node --check` 在提交前必报错** ← 这是唯一能"未跑就抓"的 |

**第一时间发现顺序(推荐):**
1. 提交前:`node --check assets/chat/chat_stage.js`(语法级,秒抓);
2. 提交前:`dart analyze`(Dart 侧没改坏);
3. 提交前:一条"占位符残留"断言——产物里不得再出现 `__KIRA_QUOTE_`、`__KIRA_CHAT_BRIDGE__`、`$kChatBridgeJs`、`__DART_INTERP` 等字样(内容等价级);
4. 真机:白屏?桥通不通?(已有的 `[bridge]`/`[TH中转]`/`[WV-*]` 探针日志就是现成的观测点)。

大白话:最坏是"一句话写错、整个脚本块死掉"的语法级事故;好在它恰恰是 `node --check` 能"未跑先抓"的那一类。所以抽离的第一道、也是最强的一道保险,就是提交前一条命令。

### 问题 7:拆多个 asset,还是一个整文件?

**推荐:一个整 HTML 骨架 + 把"最高危、最常改"的大段 JS 单独成一个 `.js` 文件;polyfill 留在 HTML 内联。不推荐把 css/html/js 拆成要靠 `<script src>`/`<link href>` 才能算数的多文件。**

理由:
1. 页面是经 `InAppWebViewInitialData` + `baseUrl: about:blank` 以**字符串**形式喂进去的(P0-1 问题 4)。在 `about:blank` 下,`<script src="...">` 的相对路径**解析不到 asset 文件**,拆成外链文件是白拆。所以任何落地形态最终都要由 Dart 把 JS **填回到字符串里**。
2. 因此折中最优:`.html` 骨架放 `<head>`/`<style>`/`<body>` 骨架 + 3 个占位;最长的**主 `<script>` 正文**单拆成 `chat_stage.js`(外面可直接 `node --check`),由 Dart `replaceAll` 一个 `__KIRA_STAGE_JS__` 占位填回。
3. `polyfill` 必须**先于**一切业务脚本在 `<head>` 跑,与 body 末尾的主脚本执行顺序不同,不能和主脚本合成一个 `.js`。它又很小(约 26 行、长期不变),**留在 HTML 内联**成本最低。
4. `kChatBridgeJs`(4977 字符的桥)可并入 `chat_stage.js`,或单独一个 `chat_bridge.js`,也可继续留在 Dart——三者皆可,倾向"也抽成 asset"让 `node --check` 一并覆盖。

大白话:别拆成网页外链那样(about:blank 下不认相对路径);"一个 html 骨架 + 一份大 JS 文件、Dart 拼回去"是性价比最高的形态,既拿到 `node --check 单文件直查`,又不用为 polyfill 的执行顺序发愁。

### 问题 8:α 与 P1 当年若有这把尺子,能提前发现吗?

**能。这是本步最重要的实证发现——两个失败分支都含同一处 JS 语法错误,`node --check` 一跑就报错。**

做法:把两个分支的 shell 用同一套提取脚本还原出 JS(P0-2 的脚本改造支持传入文件路径),跑 `node --check`。原始输出:

```powershell
# backup/p1-failed (P1-A / P1-B)
node --check p1_out.js
# → 退出码 1,SyntaxError:

  p1_out.js:1010
              _pre.textContent = (((m && m.prose) || '') + '
                                                           ^
  SyntaxError: Invalid or unexpected token

# backup/c1-alpha-failed (α / C1-T1..T5)
node --check c1_out.js
# → 退出码 1,SyntaxError(同一处):

  c1_out.js:1012
              _pre.textContent = (((m && m.prose) || '') + '
                                                           ^
  SyntaxError: Invalid or unexpected token
```

根因:两个分支在同一段"降级占位"代码里写了

```dart
_pre.textContent = (((m && m.prose) || '') + '\n' + ((m && m.html) || '')).slice(0, 4000);
```

(源文件 `backup/c1-alpha-failed:.../webview_chat_stage.dart:4288`,P1 同段)。**这是 Dart 三引号字符串里的 `\n`**——Dart 把它折成**真换行**,于是抽出来的 JS 里这行变成了:

```js
_pre.textContent = (((m && m.prose) || '') + '
' + ((m && m.html) || '')).slice(0, 4000);
```

JS 单引号字符串不能跨行 → **整个主 `<script>` 块语法崩坏**。而主块一坏,`setMessages`/`appendToken`/`createEngineRoom` 乃至桥注册全部失效——这正是"合成 bug"里最致命的一类,也是 P0 硬约束 9 反复警告的『三层转义』(`\$`/`\\`/`${}`在 Dart 与 JS 之间)的实锤案例。

**结论(诚实版):**
- **对这次具体的失败:能。** 两个分支的 `'\n'` 语法错,`node --check` 在提交前就能定点揪出(已实证,退出码 1 + 精确行列)。
- **但尺子有边界**:`node --check` 只查**语法**。α/P1 除了这个语法错,还有大量**逻辑/运行级**改动(分段、围栏、流式、故障隔离的语义),那些"语法合法但跑起来不对"的问题,**纯语法检查抓不到**。也就是说:这把尺子能保证"不会再因为 JS 写错而整块哑火",但不能保证"逻辑一定对"。
- **尺子还不够的地方(还要补):** ① **内容等价 diff**——抽离前后 HTML/JS 逐字比(hash/diff),保证"搬出去"这一步没漏/没多/没改(这就是 P0-2 提取产物此时能起的作用:它就是标准答案,抽离后跟它 diff);② **占位符残留断言**——防漏填;③ **真机探针**(项目已有 `[bridge]`/`[TH中转]`/`[WV-1..8]`)。

大白话:上次全灭,凶手之一就是一句 `'\n'` 没写成 `'\\n'`,把整个脚本块炸成语法错误——这把尺子当时要是有,第一条命令就拦下了。但尺子只管"写得对不对语法",管不了"跑起来对不对",后者还得靠"逐字 diff + 真机看日志"补。
