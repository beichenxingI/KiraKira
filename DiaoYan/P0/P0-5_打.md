## 八、给人类的复测说明

**必须冷启动**:本改动涉及 asset + `initState` 时序,请**杀进程后重开**(不要热重载;asset 大概率不会在热重载时重读,P0-3 问题 3 已标注未验证)。

**具体步骤**:
1. 完全退出 app,重新启动。
2. 进入一个已有对话的聊天页(触发 `WebViewChatStage` + `_loadChatStageAssets` + 挂载)。
3. 看历史消息是否正常渲染(气泡、AI/用户头像、楼层、版本切换条)。
4. 发一条消息,看流式回复是否逐字追加、滚动是否自动贴底。
5. 看正文里引号/方括号等是否仍跟随主题色(q/p 两色,占位符替换点)。
6. 含 `<style/<script/<html` 的富卡片:看是否仍在 iframe 里正常加载(依赖 `injectBridge` + libs 注入)。
7. 点功能面板(生图/语音/记忆/变量/正则/气泡),看桥是否通、模型列表是否加载(依赖 `kChatBridgeJs` 桥注入)。

**什么算成功 / 失败**:
- 成功:以上 1–7 全部与改动前一致;日志里出现既有探针(`[bridge]`、`[TH中转]`、`[WV-*]`),且**没有** `聊天壳资产读取失败`、`聊天壳加载失败`(错误页)、`no JS handler`、`[dispatch错误]`。
- 失败:白屏或出现「聊天壳加载失败」红色错误页(asset 没读到)、发消息无响应(桥没注入)、引号颜色固定不变(占位符没替换)、富卡不渲染。

**失败时抓什么日志给谁看**:
- `KiraLogger` 的 `聊天壳`(tag)error 日志 → 给负责 asset/packaging 的人(判断是否资产没打进包)。
- `[bridge]`/`[dispatch错误]`/`no JS handler` → 给负责桥的人。
- `[引擎房]`/`[TH中转]`/`[WV-3]`(setMessages 模式)/`[WV-7]`(高度异常)→ 给负责渲染管线的人。
- 附上 `dart analyze` 该文件输出 + `node --check` 结果,证明产物在机器检查层面干净。

## 九、我没能验证的部分

1. **真机/模拟器运行**:未跑 app。所有「行为不变」是静态推断 + 两份独立字节等价自证,不是运行时验证。复测说明(第八节)是唯一能覆盖此处的下一步。
2. **CRLF 换行是否构成字节级差异**:`.gitattributes`(`* text=auto`)+ `core.autocrlf=true` 会让 git 在 Windows 工作区把 asset checkout 成 CRLF;而原 `_htmlShell()` 是 Dart 编译期把 CRLF 归一成 LF 的字符串。`rootBundle.loadString` 不做换行归一。功能上 HTML/JS 把 CRLF 与 LF 都视为空白(shell 内无跨行字符串/正则,已核实),但**字节层面 LF≠CRLF,且我无法运行 app 确认**。这是本次「纯搬迁」目标上的一个待确认点,建议人类在复测时留意;若要强保证字节一致,可在 `.gitattributes` 增加 `assets/chat/*.html text eol=lf` / `assets/chat/*.js text eol=lf`(本轮未擅自动 `.gitattributes`)。
3. **`pubspec` 的 `- assets/` 是否确实递归收录 `assets/chat/**`**:据 Flutter 官方行为「目录条目递归包含子目录」推断已覆盖,故未新增声明;**未通过 `flutter build` 实测确认**。若复测发现资产读不到,优先检查这一条(补救:加 `- assets/chat/`)。
4. **`node --check` 只验语法,不验运行**:通过≠能跑;`sendToFlutter`/`registerBridgeHandler` 等运行时对象一律不查(P0-2 同此边界)。
5. **`_loadChatStageAssets` 失败重试路径**:修正 1 保证失败后 `_chatStageLoaded` 仍 false、下次挂载会重试,但「重试何时触发」依赖再次进入聊天页,未在真机验证。
6. **一处遗留过时注释**:`chat_bridge_js.dart:19` 的注释文字仍写「在 _htmlShell 的 <script> 里插入 kChatBridgeJs」,现已过时(运行时走 asset)。本轮按范围未改该注释,仅加了修正 3 要求的那一行。
