## P0 级：核心功能缺失 (必须修复)

### 1. 统一 EJS 渲染管线 — 展示侧与开场白补全

**问题**：
- 发送给 LLM 的消息走完整 EJS 渲染 (`_renderEJSInMessages` → `_handleRenderEJS` → `window._TH.substituteParams`)
- **展示给用户的消息完全跳过 EJS** (`_serializeMessage` 只做正则+Markdown)
- **角色开场白/备选开场白完全跳过 EJS** (`createChat` 仅 `MacroService.process` 宏替换)

**影响**：
- 用户看到原始 `<% if %>...<% } %>` 控制流语法
- 开场白无法使用 EJS 变量插值/条件渲染
- LLM 看到渲染后内容，用户看到未渲染内容 → 认知不一致
- MVU 读取 `window.chat` 也是未渲染内容

**建议方案**：
```dart
// 方案 A: 在 _serializeMessage 中接入 EJS 渲染 (推荐，改动最小)
Future<String> _renderEJSForDisplay(String text) async {
  if (!_controller) return text;
  return await _handleRenderEJS({'text': text}); // 复用现有桥
}

// _serializeMessage 中:
// rawContent = await _renderEJSForDisplay(rawContent);
// 然后再跑正则 + Markdown
```

**替代方案 B**：在 `chat_providers.dart` 入库前预渲染 (存渲染后 HTML)，但破坏 "源文本不变" 原则。

**实施要点**：
- 异步渲染需并发控制 (批量消息并发请求引擎房)
- 缓存机制：同一消息只渲染一次，swipe 切换复用
- 开场白在 `createChat` 时同步渲染 (或首次展示时懒渲染)

**预期收益**：EJS 模板在所有场景统一生效，消除"LLM 看到 vs 用户看到"不一致。

### 2. 补全 `ejs_stub.js` 核心存根

**问题**：`ejs_stub.js` 多个核心导出为空存根，高星卡依赖这些功能会静默失效：

| 存根 | 现状 | 影响 | 优先级 |
|------|------|------|--------|
| `loadWorldInfo` | `async()=>null` | 世界书完全失效，高星卡核心功能 | **最高** |
| `yaml.load/dump` | 空对象 | 变量系统 `initvar` 失效，MVU 变量初始化失败 | **高** |
| `getRegexedString` | 原样返回 | 正则脚本在 MVU/EJS 侧失效 | **中** |
| `SlashCommand` 系列 | 空类 | 斜杠命令在引擎房失效 | **中** |
| `world-info.js` 系列 | 空对象 | 世界书完整 API 缺失 | **高** |

**建议方案**：
- **短期**：将 Dart 侧已实现的功能通过 `__thCall` 桥接暴露给 stub
  - `loadWorldInfo` → `th_wiGetLorebooks` + `th_wiGetEntries`
  - `yaml.load` → Dart 侧 YAML 解析 (已有 `yaml` 包)
  - `getRegexedString` → `RegexService` 桥接
- **长期**：完善 `ejs_bundle.js` 确保稳定导出 `substituteParams`，减少对 stub 依赖

**实施要点**：
- stub 导出函数改为 `async` 调用 `__thCall` 等待 Dart 返回
- 需处理同步/异步边界：EJS 运行期可能同步调用 `substituteParams`

### 4. 引擎房/卡片桥接脚本共享化

**问题**：
- `tavern_helper_facade.dart` 生成的门面 JS 注入引擎房 (一次)
- `injectBridge` 每张卡片都内联一套 polyfill + 通信桥 + 高度上报 (~3KB/卡片)
- 两套代码重复度 > 80%

**建议方案**：
```javascript
// 方案：提取共享运行时库 window.__KIRA_RUNTIME
// 引擎房创建时注入一次，卡片 iframe 通过 parent 引用

// 主文档/引擎房注入一次：
window.__KIRA_RUNTIME = {
  polyfill: { localStorage, sessionStorage, console },
  thCall: createThCall(frameId),
  reportHeight: createHeightReporter(frameId),
  // ...
};

// 卡片 iframe 只需：
const rt = parent.__KIRA_RUNTIME;
Object.assign(window, rt.polyfill);
window.__thCall = rt.thCall.bind(null, frameId);
window.reportHeight = rt.reportHeight.bind(null, frameId);
```

**收益**：卡片 iframe 体积减少 ~70%，内存占用降低，维护单一代码源。

### 5. 统一消息序列化/渲染入口

**问题**：
- `_serializeMessage` (展示用) / `_serializeMessagesForMvu` (MVU用) / `_handleGetMessages` (桥接用) 三套序列化逻辑并存
- 字段不一致：`swipes_data` vs `variables` vs `swipes`，易导致 MVU 读取异常
- EJS 渲染只在发送侧，展示侧缺失

**建议方案**：
```dart
// 统一入口：MessageSerializer 类
class MessageSerializer {
  final EJSRenderer? ejsRenderer;
  final RegexService regexService;
  
  // 核心方法：按用途序列化
  Future<Map> serializeForDisplay(ChatMessage m);      // UI 展示：EJS+正则+MD
  Future<Map> serializeForMvu(ChatMessage m);          // MVU 同步：原文+swipesData
  Future<Map> serializeForBridge(ChatMessage m);       // 桥接查询：按需
  
  // 统一 EJS 渲染
  Future<String> _renderContent(String raw, bool isForLLM);
}
```

**收益**：消除字段不一致 Bug，EJS 渲染统一入口，便于测试和维护。

## P2 级：架构分层优化 (中长期)

### 6. 拆分 `webview_chat_stage.dart` 巨石 (4584 行)

**现状**：单文件承担过多职责：
- WebView 生命周期管理
- 资源加载/注入 (7 种资源)
- 引擎房创建/销毁
- 消息序列化/推送/增量更新
- 桥接处理器注册 (20+ handlers)
- 输入栏/面板/图片选择/导入导出
- 键盘/生命周期/滚动监听

**建议拆分**：
```
lib/presentation/screens/chat/
├── webview_chat_stage.dart          // 主组件 (~500 行)，组合子组件
├── webview_lifecycle.dart           // WebView 挂载/卸载/资源预加载
├── webview_injection.dart           // 7 种资源注入逻辑
├── engine_room/
│   ├── engine_room_controller.dart  // createEngineRoom/resetEngineRoom
│   ├── engine_room_resources.dart   // 门面/MVU/EJS/LIBS 资源管理
│   └── trinity_sync.dart            // chat/chat_metadata 同步
├── message_renderer/
│   ├── message_serializer.dart      // 统一序列化 (含 EJS)
│   ├── message_pusher.dart          // _pushMessages/_appendNewMessages
│   └── inject_bridge.dart           // injectBridge JS 生成
├── chat_bridge_handlers.dart        // 20+ bridge handlers 集中管理
├── input_bar.dart                   // 输入栏/面板/附件
└── scroll_keyboard.dart             // 滚动/键盘/生命周期观察
```

**收益**：单文件 < 500 行，职责单一，便于单元测试，团队并行开发无冲突。

---

### 7. Provider/Service 层解耦

**问题**：
- `chat_providers.dart` 3056 行，混合了：状态管理、上下文构建、LLM 调用、RAG、摘要、生图、向量检索
- `LLMService` 直接依赖 `EJSRenderRegistry` (presentation 层类型)，违反分层
- `MacroService`/`VariablesService` 在 `_buildContext` 中交织调用，难以测试

**建议方案**：
- **拆分 Provider**：`ChatContextBuilder` (构建上下文) / `ChatGenerationController` (生成流程) / `ChatMessageRepository` (消息持久化)
- **EJS 渲染器接口下沉**：`domain/services/ejs_renderer.dart` 定义接口，`presentation` 实现
- **引入 UseCase/Interactor 模式**：`SendMessageUseCase` 封装发送全流程，Provider 只管状态

## P3 级：基建完善 (长期)

### 8. MVU/EJS 版本管理与验证机制

**现状**：
- `mvu_bundle.js` / `ejs_bundle.js` / `ejs_stub.js` 版本无管理
- 验证脚本仅 `console.log`，无自动化断言
- EJS Bundle 是否导出 `substituteParams` 运行时才知

**建议**：
- `pubspec.yaml` / `package.json` 同步版本号
- 构建时生成 `version.json`，注入 `window.__KIRA_VERSIONS`
- 单元测试：Node 端跑 `ejs_bundle.js` 验证导出
- 启动时自动化验证：`substituteParams('<% if(1){%>ok<%}%>') === 'ok'`

## 9. 接口设计不合理清单

| 接口 | 问题 | 建议 |
|------|------|------|
| `LLMService.generate()` 丢弃 reasoning | 向后兼容导致信息丢失 | 废弃，统一用 `generateWithReasoning` |
| `RegistryEJSRenderer` 依赖 `EJSRenderRegistry` (presentation) | 分层倒置 | 接口下沉到 `domain`，实现上浮 |
| `ChatBridge.on/onRequest` 字符串类型 | 无类型安全 | 定义 `BridgeType` enum + codegen |
| `_serializeMessage` 返回 `Map<String,dynamic>` | 无类型约束 | 定义 `SerializedMessage` class + freezed |
| `MacroContext.fromData` 参数过多 (7 个) | 易误用 | Builder 模式或记录类 |
| `PromptSectionType` 与注入位置耦合 | 扩展困难 | 策略模式分离注入逻辑 |
