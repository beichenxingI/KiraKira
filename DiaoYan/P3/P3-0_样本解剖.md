## Q5(修正后):受控出口设计(冲突已成立,不需再论证)

冲突已成立:`parent.document` 4 处(其中启用脚本 1 处有效)证明卡**会跨帧操作父文档**。设计直接回答"受控出口"。

### 5.1 谁分配容器、挂在 shell 哪个节点

- shell 在 `__kira_root` 之外、`<body>` 下新增一个**宿主容器** `#__kira_card_host`(只读 shell 侧,由我们加)。卡申请的"父文档节点"统一挂到这里,不放开整个 `parent.document`。
- 卡若要求挂到 `#user_avatar_image`(读头像),我们不改 -- 那是"读",不是"挂节点";挂节点的需求(悬浮球)由受控 API 满足。

### 5.2 消息销毁/视口摘除时球怎么回收(防 350 楼 350 球)

- **球的生命周期必须跟消息 iframe 走**:若消息级 iframe 隔离成立,球挂在自己的 iframe 内,iframe 销毁(消息移除/视口摘除)球自动销毁,天然不会遗留。
- 若球必须挂父文档(受控宿主),则**宿主容器按消息 id 分舱**,消息销毁时删对应舱;视口摘除时先摘舱再摘楼,滚回时按 id 重建舱。

### 5.3 重复创建怎么去重

- 宿主容器内按 `data-msg-id` 分舱,创建前先 `querySelector('[data-msg-id=...]')` 查重,已存在则复用/更新而非新增。

### 5.4 一个卡的球能碰到别的卡的球吗(应该不能,怎么保证)

- **消息级 iframe 隔离**下,每卡独立 iframe,DOM 不共享 → 天然不能。
- 若受控宿主要在父文档,则每个卡的球只允许操作自己的 `data-msg-id` 舱;卡脚本发往父文档的节点操作,由桥**过滤/重定向**到它自己的舱,跨舱访问被拒绝。

### 5.5 "直接放开 parent.document" vs "受控出口" 各自失败模式

| 方案 | 失败模式 |
|---|---|
| 直接放开 `parent.document` | 卡 A 的球可能命中卡 B 的 id、或 shell 的 id → P1-C1 刚修好的"劫持"以另一种形式复发;350 楼可能 350 个球全堆主文档,`dupIds`/节点数爆炸;无清理、无去重、无隔离。**不可取** |
| 受控出口(宿主 + 分舱 + 桥过滤) | 实现成本高;若卡脚本硬编码访问非受控节点(直接 `parent.document.body.append`),桥**拦不住**(只能靠 iframe 隔离兜住);失败模式是"某些刁钻卡的球仍挂到主文档"而非"污染其它消息",危害受限 |

**结论**:P3-1 动手前必须定——**优先走"消息级 iframe 隔离"**(球留在自己 iframe 内,最干净、失败面最小);受控出口只作为"个别必须挂父文档的球"的补充,且必须有分舱 + 去重 + 回收。

## Q7(新增):localStorage 依赖会不会让球失忆

### 7.1 我们注入的 localStorage 是什么

[我们代码]:`injectBridge`(char_stage.html 489 起)里 polyfill 覆盖 `window.localStorage`,是**内存态**(`var _s={}` 存 `getItem/setItem`,见 chat_stage.html 498 区域):

```js
var _s={};
window.localStorage = {
  getItem:k => _s[k]||null,
  setItem:(k,v)=>_s[k]=String(v),
  ...
}
```

### 7.2 卡用 localStorage 存了什么(**[样本]**)

- `daoyuanCharacterPresets`(regex_7)—— 开局创造人物的预设存档
- `daoyuan_custom_portraits`(regex_6:881)—— 自定义立绘(base64 图,可能很大,见 875 行"接近 5MB"告警)
- `daoyuan_wx_presets` / `daoyuan_wx_settings` / `daoyuan_wx_lore_selected` / `daoyuan_wx_read_states` —— 状态栏的各种设置/已读状态

### 7.3 "iframe 重建 → 球每次回初始位置"这个推断成立吗?

**[推测:成立,但需细化]**:`localStorage` 是内存态,iframe **销毁重建**(消息级 iframe 化、或卡片 `about:blank` 虚拟化、或 reload)后 `_s={}` 清空 → 卡读 `getItem` 得到 null → 走 `|| {}`/`|| '{}'` 默认值 → 球回到初始位置/预设清空。所以"失忆"是**结构性成立**的。
但注意:当前(非消息级 iframe)下,卡片 iframe 在**同一次会话内不重建**时,内存 `_s` 是持久的;只有重建才失忆。

### 7.4 若真要持久化,最小改动(只出方案)

- **桥转发到 Dart 侧存储**:injectBridge 的 `localStorage.setItem/getItem` 改为 `sendToFlutter` 发桥请求,Dart 侧写 `path_provider` 文件或共享偏好。这是最小方案,但涉及桥协议新增字段(禁区"不许改桥协议字段"——需单独立项,不算 P3-0 范围)。
- 或在消息级 iframe 化时,iframe 不销毁(只摘 DOM),靠"iframe 常驻 + 只 toggle display"避免重建失忆(但这与 P2 视口窗口化的"摘 DOM"冲突,需权衡)。

## 最小可跑路径(Q5 依赖排序总结,只出设计)

要让悬浮球显示并拖动,最少需要(按依赖):

1. **消息级 iframe 承载**(球留在自己 iframe 内,隔离 + 生命周期) —— 或先验证"卡脚本能完整加载"(解决 CDN import 打包问题)。
