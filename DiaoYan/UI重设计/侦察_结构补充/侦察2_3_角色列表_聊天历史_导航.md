### d) 搜索/筛选/多选结构与分页共存方案

- 现状过滤发生在 **build 层**:状态只存 `_searchQuery`(State 成员),`charactersAsync.when(data:)` 里本地 `where()` 过滤 name/description(L371-376)。多选 `_selectionMode`/`_selectedIds` 也是同 State 内的纯 UI 状态,长按进入、点选切换、空集自动退出;AppBar 切换为选择模式(批量删/ZIP 导出)。
- 另有一套**未被该页使用**的 provider 层筛选:`lib/presentation/providers/character_filter_providers.dart`(`characterFilterProvider` + `filteredCharactersProvider`,支持标签/收藏/排序 6 档)——可作为后续把过滤上移 provider 层的现成基础。
分页方案建议:
  1. **方案1(推荐,最小改动):页内切片,逻辑全集不变**。搜索过滤仍先作用在全量列表得到 `filtered`,再 `filtered.skip(page*N).take(N)` 喂给 GridView;底部加翻页条或改用 `gridDelegate`+自动加载。多选中 `_selectedIds` 持的是 ID 集合,与当前页解耦,翻页/搜索不清选择即可共存;搜索词变化时重置 `page=0`。
  2. **方案2:过滤/分页整体上移 provider 层**——复用 `filteredCharactersProvider` 派生 `pagedCharactersProvider(filtered, page, pageSize)`,UI 无状态。优点是切尺寸/换搜索不丢状态且可测试;代价是要迁移现有 build 层过滤逻辑。
  - 共同点:**选择状态按 ID 存、不随页切片**,是搜索/多选/分页不互踩的关键。

## 3. 任务C:导航外壳

### a) app_shell 结构

- 文件 `lib/presentation/widgets/common/app_shell.dart`,`AppShell` 自用 Scaffold:**无 AppBar,无黑框**(背景 `DesignTokens.darkBackground`)。body 为 `Stack`:①业务 child;②高级模式悬浮球 `_AdvancedFab`(right16/bottom100);③底部 `_KiraNav`(Positioned 贴底)。
- `_KiraNav`:居中胶囊条(maxWidth 460,高 56,实色 surface+细边+阴影)四项 `角色卡/聊天回忆/API服务/设置`,中间镂空放圆形凸起"聊天"主按钮(52px,DesignTokens.primary)。选中态由 `_calcIndex` 按当前路径前缀算出(`/characters`→0,`/chats`→1,`/`与`/chat/`→2,`/ai-config`→3,`/settings`→4),点击 `context.go(...)` 切换。

### b) 路由现状(**与任务预设不符的重要发现**)

- `lib/presentation/router/app_router.dart`:**全库没有任何 StatefulShellRoute**(grep 0 命中)。用的是**普通 `ShellRoute`**(单 `_shellNavigatorKey`,builder 包 `AppShell`),下挂 5 条平级 GoRoute:`/chats`→HomeScreen、`/`→MainPage(时间+背景首页)、`/characters`、`/ai-config`、`/settings`,均走 `_buildTabPage` = CustomTransitionPage 纯 **FadeTransition**(300ms,curveSlide)。无 branches、无每分支 navigator key、**无 IndexedStack**——每次切 tab 都是整页 go 替换+淡出淡入,不保留 tab 内滚动/导航栈状态。聊天详情 `/chat/:id` 是 rootNavigator 全屏页,不在 shell 内。

### c) PageView 横滑兼容性结论

- **结论:当前结构下"部分兼容,且比现在传言的 StatefulShellRoute 场景更好做",但整体不推荐大改。**
- 有利点:因为不是 StatefulShellRoute,没有"每 branch 独立 Navigator 塞进 PageView 会脱离 ShellRoute 管理"的坑——5 个 tab 本来就是平级页面,天然可改成一个自管 `PageView`。
- 可行做法:
  1. **PageView + 手动 go(推荐折中)**:AppShell 内嵌 PageView 只放要横滑的两页(角色 /chats 列表),onPageChanged 里 `context.go()` 同步 URL 与底栏选中态,反向在 `_calcIndex` 时 animateToPage。两页均无栈内子路由(详情都走 rootNavigator push),状态丢失风险小;但 Hero 动画 `character-<id>` 跨页不受影响,滚动位置需 PageView 的 keepAlive(AutomaticKeepAliveClientMixin)保住。
  2. **彻底自管 stack**:放弃 ShellRoute,AppShell 内 IndexedStack+自维护分支 Navigator(即手写 StatefulShellRoute)。自由度最高,但要重做深链/返回栈,成本高。
- 风险点:官方 go_router 的推荐方向恰恰相反——横滑需求通常做法是用 `StatefulShellRoute` + `goBranch` 配合,而社区在 PageView 里复用 ShellRoute branch 是已知坑;本项目因没采用 StatefulShellRoute 反而避开该坑。若只做"角色页↔聊天回忆页"双页横滑,方案1 成本可控(改动集中在 app_shell.dart);若要五页全横滑,需评估与中间凸起按钮、扩展 FAB 的手势冲突。
- 另注:`/`(MainPage)与 `/chats`(HomeScreen)是两个不同页面却共用"聊天"语义入口,底栏中间圆球指向 `/`,横滑设计需先明确"聊天页"指哪一个 index(底栏 index2=/, index1=/chats)。

## 4. 汇总:三个关键结论

1. **角色页分页可行,建议默认每页 20(2 列×10 屏内滚动分页)或干脆不做硬分页只做"每页数量=列数提示"**:数据是 SQLite 全量内存列表(数量有限、无 LIMIT),过滤在 build 层、选择按 ID 存,页内切片方案改动最小;设置项用 shared_preferences 持久化,模板照抄 `advanced_mode_provider.dart`(键风格 `character_grid_page_size`)。若"每页数量"实指**单页卡片数显示密度**,更简单的是开放 crossAxisCount(2/3/4)设置而非真分页。
2. **角色卡改造涉及文件(全部可改,无禁区触碰)**:
   - `lib/presentation/screens/character/character_list_screen.dart`(网格参数 L523-528、卡片 `_CharacterGridCard` L720-901、过滤 L371-376、多选 L39-98)
   - `lib/presentation/providers/character_providers.dart`(数据源,如需上提过滤)
   - `lib/presentation/providers/character_filter_providers.dart`(现成筛选/排序 provider,可复用)
   - 新增:pageSize/列数 provider(模板 `advanced_mode_provider.dart`)+ 聊天历史列表在 `lib/presentation/screens/home/home_screen.dart`(`_ChatListView`/`_ChatListTile`,可改)。
3. **横滑:部分兼容、谨慎推荐只做双页版**。项目是普通 ShellRoute(非 StatefulShellRoute,无 IndexedStack/分支 Navigator),tab 即平级路由+Fade 转场;PageView 内嵌两页 + `context.go()` 同步可行且无 branch-Navigator 坑,但要处理 keepAlive 与 URL/底栏选中同步,五页全横滑不建议。
