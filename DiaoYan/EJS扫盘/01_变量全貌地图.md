## 总览:三层变量其实有「三个世界」

```
世界A:Flutter 权威存储(落盘真相)
  global  -> SharedPreferences 'global_variables'
  chat    -> SharedPreferences 'local_variables_<chatId>'
  message -> ChatMessage.swipesData (per-swipe MvuData 数组)
             -> drift messages 表 swipes_data_json 列
  [VariablesService 单例 + ChatRepository]
        |  (1) __varSync 推送 宿主->引擎房   (2) th_setVars 回写 引擎房->宿主
世界B:引擎房镜像(webview iframe 内,易失)
  _TH.__varCache {global, chat, message[mid]}
  + EJS 标准对象同源回填:
    window.extension_settings.variables.global
    window.chat_metadata.variables
    window.chat[mid].variables[swipe_id]
  [tavern_helper_facade.dart]
        |  import(同一 stub blob)
世界C:EJS dist / MVU bundle(消费者)
  MVU 读镜像(getVariables 同步)、写走桥(setVariables 异步)
  EJS dist 疑似只加载不消费(见 00 文档第3节)
```

**没有「Trinity 合并器」这种东西**——不存在把三层合并成单一视图的函数。所谓 Trinity 只是引擎房里三个标准 ST 对象的初始化 + 镜像回填(webview_chat_stage.dart 内注释「Trinity: 为 EJS/dist 准备标准 ST 对象」)。三层各自独立存储,读哪层给哪层。

## 地图 1:变量底座(EJS 与 MVU 的公共地基)

### 1a. 存储(世界A)

| 层 | 落盘位置 | 内存持有 | 代码锚点 |
|---|---|---|---|
| global | SP 键 global_variables | VariablesService._globalVariables | variables_service.dart 的 _loadGlobalVariables/_saveGlobalVariables |
| chat | SP 键 local_variables_加chatId | _localVariables[chatId] | 同上 loadLocalVariablesFromPrefs/saveLocalVariablesToPrefs |
| message | drift messages 表 swipes_data_json 列(默认空数组) | ChatMessage.swipesData(List<Map> 每swipe一份) | database.dart swipesDataJson 列;chat_repository.dart addMessage/updateMessage/_messageFromRow |

- 进入聊天时恢复局部变量:chat_providers.dart 内「恢复本聊天的局部变量(酒馆助手 getVariables 存档)」处调用 loadLocalVariablesFromPrefs。【实证】
- 全局变量的加载是懒的:只有 globalVariablesProvider 首次被 watch 才触发 initialize()(variables_providers.dart 的 GlobalVariablesNotifier._loadVariables)。providers_registry 只是 export 不构成 watch。见 03 问题清单 P5。【实证】
- 兼容旧通道:loadLocalVariablesFromMetadata/exportLocalVariablesToMetadata(chat metadata variables 键),导出方向当前无调用方。【实证】

### 1b. 读链(谁在读)

1. Flutter 宏(prompt 组装):chat_providers.dart 的 processMacros() = MacroService.process 后接 VariablesService.processVariableMacrosSync;async 版走 processVariableMacros。作用对象:世界书条目、prompt sections、开场白创建(createChat 内「Process macros in the greeting」)。【实证】
2. Flutter 宏(另一份实现):macro_service.dart 的 _processVariableMacros,支持 setvar/getvar/setglobalvar/getglobalvar 四种,「一段文本处理完统一落盘一次」。与第 1 条是两套并存实现。【实证】
3. WebView API 读:
   - facade _TH.getVariables(option) 同步读 __varCache;type=message 支持 message_id/latest/负数索引(__resolveMid)。【实证】
   - Dart 桥 th_getVars(_handleGetVariables)只支持 global/chat 两层,没有 message 分支。【实证】
   - MVU 实际读 facade 本地镜像版(同步语义),不走桥(facade 注释:「MVU 的 getVariables/getLastMessageId 是同步调用」)。【实证】
4. 设置页:variables_settings_screen.dart。【实证】
### 1c. 写链(谁在写)

1. Flutter 宏 setvar 等 → setLocalVariable/setGlobalVariable → SP 落盘。
2. MVU 写(message_received 点火后解析 _.set 指令):

```
MVU replaceVariables / updateVariablesWith (type:"message", 常不带 message_id)
  -> __thCall("setVariables"/"replaceVariables")
  -> 外层 typeMap: setVariables 与 replaceVariables 都映射到 'th_setVars'
     [webview_chat_stage.dart 的 typeMap]
  -> _handleSetVariables:
       type==message -> 定位目标消息(有效 mid 用之;缺失落最后一条,
          注释明说「契合 getLastValidVariable 从末尾回溯的读取语义」)
          -> newSwipesData[swipeId] = vars   (整份替换该 swipe)
          -> notifier.updateMessageSwipesData -> DB 落库
          -> _syncVarsToEngine('message',...) 回填引擎房镜像
       type==global/chat -> VariablesService 逐 key insertOrAssign + SP 落盘
```

注意两个语义细节【实证】:
- replaceVariables 在真酒馆是整表替换,这里被路由到与 setVariables 相同的 handler:chat/global 层实际是逐 key 合并(非替换);message 层倒是整份替换。与上游语义有偏差,MVU 若依赖「replace 会删掉多余 key」会踩坑。
- facade 的 updateVariablesWith(updater) 是在 iframe 内跑 updater、只把新值过桥(facade 注释:「updater 是 MVU 传入的函数,不能过桥,必须在 iframe 内跑」)。镜像先更新再落库,落库失败时镜像与 DB 可能短暂不一致(无回滚)。【实证+疑似】

### 1d. MVU 侧专项

- swipesData 结构(MvuData):stat_data / schema / initialized_lorebooks / delta_data / display_data。空卡兜底:_serializeMessagesForMvu 给第 0 条消息在 swipesData 为空时种一份全空的 MvuData 基座,注释说明 MVU 的 isMvuData 要求同时有 stat_data 和 schema 否则直接 return(锚点:「MVU 的 getLastValidVariable→isMvuData 要求本子里同时有 stat_data 和 schema」)。【实证】

- MVU 设置面:MvuSettings(data/models/mvu_settings.dart),经 facade 以 SillyTavern.extensionSettings.mvu_settings 注入(更新方式/额外模型解析配置/破限方案/max_chat_history/模型来源/api地址/密钥/模型名称)。持久化:drift kv 表 + SharedPreferences 双写(mvu_settings_providers.dart 注释「SharedPreferences 兜底/迁移,双写保证密钥等关键数据可备份」)。【实证】
## 地图 2:EJS 渲染管线(卡壳主战场)

### 2a. 引擎初始化链(onLoadStop 顺序,webview_chat_stage.dart)

```
_injectCompatLibs      lodash/jquery/toastr 注入外层 window.__KIRA_LIBS
_injectMacroValues     window.__KIRA_MACRO_VALUES {user,char}
_injectEngineFacade    buildTavernHelperFacadeJs -> window.__ENGINE_FACADE_JS
_injectMvuBundle       mvu_bundle.js(base64,可被替换task)-> window.__KIRA_MVU_BUNDLE

_injectEjsBundle       ejs_bundle.js -> window.__KIRA_EJS_BUNDLE

```

引擎房 iframe 内部(createEngineRoom):
1. blob HTML:lodash + jquery + toastr 真库内联;__KIRA_MACRO_VALUES/__KIRA_CHAT_ID;facade JS;
2. 「Trinity: 为 EJS/dist 准备标准 ST 对象」:window.chat=[] / chat_metadata={variables:{}} / extension_settings={variables:{global:{}}};
3. __chatMessages=[] + __thEvent 监听(填 __chatMessages、同步灌进 window.chat Proxy 目标、转 TavernHelper.eventEmit);
4. 300ms 后自触发 chat_changed;
5. iframe load 后依次注入:MVU module → 错误捕手脚本 → stub blob → dist blob(16 条 import 路径全部替换为同一 stub URL)。

「四缸 finit/vinit/uinit/einit」:全仓检索无此命名(grep 仅命中 Definition 之类的误配)。【待验证:疑为历史方案/其它项目术语】

### 2b. 渲染入口 _renderEJSInMessages(llm_service.dart)

【实证】逐条:
- 遍历 messages,不过滤 role(system 也渲染);content 非 String 或为空则原样保留;
- 每条 content 调 _ejsRenderer.render(content) → RegistryEJSRenderer → EJSRenderRegistry.current → 聊天页注册的 fn → th_renderEJS;
- 只在两个调用点:generateWithReasoning(「EJS 渲染:发给 LLM 前先跑一遍 EJS」)与 generateStreamWithReasoning(「流式生成前先跑一遍 EJS」)。

🔴 th_renderEJS 的真身(_handleRenderEJS):只执行 window._TH.substituteParams(text),即 facade 手写的 {{user}}/{{char}}/<user>/<char> 宏替换。【实证】
→ **`<%- 插值 %>` 与 `<% if 控制流 %>` 在整条 prompt-out 管线上都不存在真执行**。注释写「发进引擎房跑 dist 的 EJS」与实现不符。
### 2c. 触发时机链(Dart → 引擎房的点火全集)

【实证】全仓 __emitToEngine 调用点只有 4 处 + 引擎房自fire 1 处:

| 事件 | 点火处 | 携带 |
|---|---|---|
| generation_started | _sendMessage(「触发 MVU initCheck」) | 全量 msgs 序列化 |
| generation_started | isGenerating false→true watcher(「用户发消息 → isGenerating false→true」) | 同上 → **同一轮生成会双发** |
| message_received | isGenerating true→false watcher(「AI 回复完成 → 通知引擎房 MVU 解析新回复、更新变量」) | [lastIdx] + 全量 msgs |
| chat_changed | 进入聊天 _pushMessages 后(「开场白就绪后主动填充 __chatMessages 并触发 chat_changed,让 MVU initCheck 重跑一次」) | 全量 msgs |
| chat_changed | 引擎房创建后 300ms 自fire(「[引擎房] 自触发 chat_changed」) | 无 msgs |

- **GENERATION_AFTER_COMMANDS / CHAT_COMPLETION_SETTINGS_READY / CHARACTER_MESSAGE_RENDERED / USER_MESSAGE_RENDERED / GENERATION_ENDED / MESSAGE_SENT / STREAM_TOKEN 系列:常量表里都有名字(facade tavern_events 表 + 外层另一份表),但 Dart/facade 层从不 emit。**监听它们的一切逻辑静默不跑。【实证】bundle 内部是否自产部分事件【待验证】。
- eventSource.makeFirst/makeLast 真实语义:facade 实现 = 本地桶 unshift/push(eventMakeFirst/eventMakeLast),与 ST「插队/殿后」语义形似;但引擎房是单脚本单桶,无竞争者,实际等价 eventOn。【实证】

### 2d. 两条管线悬案:开场白 vs LLM 消息

- 开场白:createChat 时 MacroService.process 宏替换后存库(swipes 数组,swipe0 主开场白,1+ 备用);显示走 _pushMessages → setMessages 下发 webview。【实证】
- LLM 消息:发送前 prompt-out 经 _renderEJSInMessages(实为宏替换);AI 回文入库后同样经 _serializeMessage 下发显示。【实证】
- 显示域序列化 _serializeMessage:Flutter 侧真 RegexService.getRegexedString(正则在此生效)+ markdown 转 HTML + 「旁白文字 + 完整 HTML 文档」切分,HTML 文档进独立 iframe 卡片。【实证】
- 结论:**两条管线在"EJS 层"是同一条路——都没有路**。历史现象「开场白标签能出现」最可能是标签以原文出现在 HTML 渲染中(未被渲染也未被转义),而非渲染成功;「♪ 条件分支没生效」与代码事实一致:没有任何真 EJS 执行点。【推断,显示域内部属禁区未读,标待验证】

### 2e. 静默失效点速览(逐条详见 03)

1. checkScript 未定义 → dist 的 substituteParams 永不挂载 + 「EJS 模块已注入」日志永不出现。
2. 三大钩子不 emit → 监听者全灭。
3. th_renderEJS 无真 EJS → 控制流模板原样发给 LLM 或原样显示。
4. EJSRenderRegistry 在离开聊天页时 clear(「清空 EJS 渲染函数登记(离开聊天页,回到安全态)」)→ 非聊天页调用 LLM 时渲染器为 null,_renderEJSInMessages 原样返回(不算错,但意味着后台生成无任何宏/EJS 替换)。【实证】
5. renderEJS 异常 catch 后返回原文,只留一行 info 日志。【实证】
## 地图 3:facade / 引擎房(EJS 引擎与 Flutter 宿主的边界)
