# 14 webview 改造方案与落地计划

> 纯调研，零代码改动。承接 `13_webview现状全图.md`。
> 验收唯一指标：**任何情况下不崩溃、不闪退、不错误渲染、不少/不多渲染。**
> 目标不是「让 webview 永不炸」，而是「炸了也不许全灭、正文仍可读」。

---

## B1 方案设计原则

1. **单 webview 不变**：隔离单位是同一个 webview 内的 iframe（共享 renderer，成本低），绝不是多 webview 实例。
2. **新旧并存 + 开关可切**：老路径一行不动，新逻辑挂 feature flag，默认关。
3. **先「不炸」再「加能力」**：故障隔离与正确性 > 新功能与性能。
4. **每期结束都是可用且可回退状态**。
5. **可观测性先行**：A8 里的「循环前失败面」也要有日志（WV-8 甚至 WV-8-pre）。

---

## B2 核心方案（两个候选）

### 候选甲：逐条隔离 + 定向 diff + 消息级 iframe（推荐，分三阶段演进）

**机制**：
- 阶段1「不炸」：把 A9 里「可独立修」的全做了——批量序列化兜底、逐条 try、外层 catch 不抹页、appendToken 不清块、prepend 倒序、围栏保护。
- 阶段2「定向 diff」：按稳定 `id` 做 `append/prepend/update/remove` 四原语，取消「每次交互全量重建 30 条」；diff 失败自动 fallback 全量重建。
- 阶段3「能力」：同一消息多段前端（切段器产 `[文本段, HTML段…]`），隔离粒度**消息级**（对齐上游「同消息多 script 共享作用域」），整条消息一个 iframe 承载，文本段不进 iframe。

**覆盖症状**：6（自下而上炸）→阶段1 根治；5（卡片被清）→阶段1；3（源码直出）→阶段1；2（旧消息顺序/50 条截断）→阶段1 prepend + 阶段2 diff + DOM 窗口化；1（重前端炸）→阶段3 + DOM 窗口化；4/7（多前端共存）→阶段3。**7 个症状全覆盖。**

**代价**：三阶段工作量最大；阶段2 的 diff 引擎是新建组件，需充分测试。

**风险**：中等（diff 状态双持 A6 需收敛；阶段3 与 A8#8 视口地板高度联动）。

### 候选乙：故障隔离 + DOM 窗口化，暂不做多前端

只做阶段1 + DOM 窗口化（不做 diff、不做多段）。覆盖症状 1/2/5/6/3，但**不解决 4/7**。

**代价**：最小，但人类最痛的多前端共存（症状 7 是常态需求）没解决。

**风险**：低。

**推荐**：**候选甲**，因为症状 4/7 是常态需求、且方案α已验证「消息级 iframe」这条隔离路线只在实现细节上翻车，方向本身成立。

### 各要素设计（可分散在两个候选里）

#### 1. 故障隔离（阶段1，必修）
- **逐条错误边界**：shell `setMessages` 的 for 循环内，每条消息单独 try，单条失败降级为 `<details>` 可见占位 + `[WV-8] MSG-RENDER-FAIL`，继续后续。**基线无此 try，须加。**
- **外层 catch 绝不抹页**：`setMessages` 末尾 catch 从 `root.innerText='ERR:'` 改为 `sendToFlutter('log', {text:'[WV-8] BATCH-FAIL kept-rendered …'})`，保留已渲染内容。
- **循环前失败面兜底（重点）**：
  - *序列化失败*：`_safeSerializeMessage` 回收 T1 版本（单条 try）。但**批量 `jsonEncode`/`utf8.encode` 也要try**——这是 T1 漏掉的；失败时 fallback 到「逐条 encode + 逐条发」保底（每单条再包一层）。
  - *JS 语法错误（注入）*：`_dispatch` 的双层 jsonEncode 前，对最终 `window.__bridgeDispatch(<str>)` 做一次 Dart 侧「自检」——不实际运行，但至少把 `U+2028/29` 用 `jsonEncode` 的 `toEncodable` 之外显式替换（或 shell 里 `String.prototype` 无关，直接 Dart 侧 `.replaceAll('\u2028','\\u2028')`）。此改动只影响注入，不影响协议。
  - *入口解析失败*：`setMessages` 顶层 `JSON.parse` 失败时记录 `[WV-3-pre] PARSE-FAIL`，**不静默**。
- 这些循环前失败面统一有日志，解决「上一轮连探针都打不出」的根因。

#### 2. 定向 diff（阶段2）
- 四原语（JS 新增 `registerBridgeHandler('appendMessage'/'updateMessage'/'removeMessage')`，先存在 `BridgeType` 里但基线未实现）：
  - `append`：末尾追加一条（现有 `_appendNewMessages` 已近似，但需 key 化）。
  - `prepend`：头部前插（修倒序）。
  - `update`：按 `data-id` 找到节点，重建该消息 DOM（含其 iframe）。
  - `remove`：按 `data-id` 摘除节点。
- **diff 失败自动 fallback 全量重建**：Dart 侧在一次 diff 操作后，若 JS 回传 `[WV-9] DIFF-MISMATCH`（实际节点数与预期不符），立即 `_pushMessages` 全量重建。这是「可回退」的关键。
- A6 里的双持状态（展开态/选中态/流式）在 update 时按「重建该 message DOM」整体刷新，不试图精细 diff 内部。

#### 3. DOM 窗口化（阶段2 或 3）
- 视口 ±N 之外摘除消息节点与 iframe，滚回时按 `data-html`/`data-id` 重建。
- **N 建议 = 3**（保留前后各 3 条）。依据：一屏约 4~6 条气泡，±3 保证滚过 1~2 屏仍不触发重建闪烁；进一步加大 N 收益递减，而 N 太小会高频重建拖帧。**需真机实测**：在真机观察 `[WV-5] nodes/groups/cardIframes` 随滚动增减、滚动掉帧情况来定 N。
- 已有 IntersectionObserver 只对 iframe 做 src 清空（不摘节点），可升级为「整节点摘除 + 回滚重建」，并把图片/文本也纳入。

#### 4. 同消息多段前端（阶段3，挂开关）
- 切段器产出 `List<Seg>{isHtml, html}`，保序。
- **隔离粒度=消息级**：整条消息一个 iframe，`[文本段, HTML段…]` 全部进同一 iframe 文档（共享作用域），文本段也用浅 `<p>` 包裹放进去即可（但纯文本消息**不**建 iframe，走 innerHTML 老路径）。
- **上游 ST 已核实同消息多 script 共享作用域**（播放器与控件互相调用），故隔离粒度不能是段级。
- **必须独立成期、挂开关（默认关）**，不得与前几期混做。

#### 5. 原生兜底层（需评估）
- 触发：webview 死亡（WV-6 崩溃）且连续自愈超限（T5 的 3 次），或人为主观判断渲染持续异常时。
- 形式：切到 Flutter 原生纯文本列表，直接读 `activeChatProvider.messages`，不做任何 webview 布局协商。**两层不同时工作，无多 webview 性能叠加。**
- **值得做吗**：值得，作为「正文仍可读」的最后保险（正好对上验收指标）。但优先级**次于阶段1**。
- 最小可用：`ListView.builder` + 纯文本正文；markdown 渲染可有可无。`pubspec.yaml` 已有 `flutter_markdown ^0.6.18`【实证 pubspec:60】，**无需新引依赖**，直接可用 `MarkdownBody` 或降级纯文本都行。
- 自动切换 vs 手动：**自动切换为主**（崩溃自愈超限时自动降级），手动按钮为辅助（debug 菜单加一个「切原生纯文本」入口）。
- 降级提示：页面顶部一条 SnackBar/横幅「已切换到纯文本保底模式，复杂卡片暂不可用，可点按钮重启 webview」。
- 注意：切出去后「重启 webview」需要重建 shell + 重注入 + `_pushMessages`，复用 WV-6 自愈字符串（`reload` 或重挂 `_webViewMounted`）。

#### 6. 症状 3（源码直出）修法 + 副作用权衡
- 修法：围栏摘出放正则**之后**（即正则只作用于围栏之外的文本，摘出的 ```html 块事后归还）——T3 思路。
- 副作用（用户已问）：摘出保护后，正则**再也改不到卡片内部**（包括高星卡「美化状态栏 HTML」的正则）。这个代价**可接受但不理想**。
- **两全方案**：提供「正则作用于卡片内部」的开关/或分段作用域。更稳妥的权衡：**先只保护围栏，不保护裸 HTML/文档**——即只摘 ```html 围栏块，文档级 `<html>` 仍走原逻辑（正则可影响）。这样既能治症状 3 的主因（围栏被正则破坏成 code block），又不彻底封死「正则美化卡片」。**这是推荐折中。**

#### 7. 视口高度地板修法
- 现状 `f.style.height=max(contentH+4, innerHeight)` 是为「整页 vh 卡 flex 居中」而设的地板，但会让任何带小状态栏的消息级 iframe 撑满屏。
- 修法：地板只对「显式声明需要视口舞台的卡片」生效——例如检测卡片是否含整页样式（`min-height:100vh` / `body{display:flex}` 居中）再给 `innerHeight` 地板，其余用 `contentH+4`。
- 消息级隔离下，纯文本/小卡片**不应**给视口地板。

#### 8. 流式与幂等
- `appendToken` 正确改法：首 token 建立独立 `.stream-text` 区（不清 wrap），后续 `stream.textContent += token`（T4 正确）。
- 防「多渲染」反向问题：生成结束时（`:440` 全量刷新）或 reroll 时，先移除该消息旧 `.stream-text` 再重建，确保旧流式残余不叠加。用 `data-id` 精确定位，不全局清。

## B3 测试脚手架（本轮最想要，请认真设计）

### 结论先给：**值得先做，应排在第 0 期（第一阶段里第一个落地项）。**
理由：上一轮翻车本质就是「改完只能真机手测」，脚手架把「反馈慢/覆盖窄/炸了才知道」变成「改完本地立刻知道」。

### 1. 合成消息调试页
- 入口：debug 菜单（现有功能面板里加 `navigateTo` 项，或 `_funcPanelOpen` 后隐藏手势）。
- 实现：一个 Dart 测页，输入/选择一条「预置畸形消息」→ 直接调 `_serializeMessage`（纯函数）→ 把产出的 map 喂给同一套渲染管线（不走真实对话，直接 `_bridge.send(setMessages, …)` 注入单条）。
- 效果：能立刻在真机 webview 里看到这条畸形消息渲染成什么样，而无需真实对话。

### 2. fixture 语料库
应收集的形态（存 `test/fixtures/` 或 `DiaoYan/EJS扫盘/fixtures/`）：
- 多前端混排：文本 + `<!DOCTYPE>` 文档 + `\`\`\`html` 卡片交替。
- 正则破坏围栏：正则匹配到 ``` 前后字符导致围栏降级。
- 超长消息（十万元级）。
- 畸形 HTML：未闭合标签、`<script>` 嵌套、属性含 `"`/弯引号。
- 含死循环 JS 片段。
- 超大 base64 图（几 MB 级）。
- 含 `\u2028/\u2029`、lone surrogate、`\u0001` 的消息。
- 含 `$( `、`jQuery`、`<script`、`<style` 子串的纯文本（触发 injectBridge 检测）。
- 空消息、仅 emoji、仅图片附件。

### 3. 可自动化部分（纯函数单测）
- **切段器**、**正则+围栏**、**序列化**：是否纯函数？
  - `RegexService.getRegexedString`：纯（string→string + 缓存）【实证 regex_service.dart:145】。
  - `_serializeMessage`：当前是类成员方法（依赖 `ref`/`character`/`scripts`），但**逻辑上纯**（输入 ChatMessage + scripts → 输出 map）。可重构出顶层纯函数便于测试。
  - 切段器（阶段3）：全新纯函数，天然可测。
- **test/ 目录现状**：**不存在**（无 `test/`）。`pubspec` 有 `flutter_test`（dev 依赖）【实证 pubspec:83】。需新建 `test/` + 首个测试文件。
- 结论：**可以且应该写 Dart 单测**，覆盖切段器/围栏保护/序列化兜底。这是唯一「上 CI」的自动化手段。

### 4. 渲染结果可断言性
- 从 webview **回传渲染结果快照**：在 `setMessages` 末尾 `sendToFlutter('log', …)` 已能报 `groups/cardIframes/nodes`（WV-5）。可再增加一个 `[WV-REPORT] rendered={n} iframes={m} error={e}` 的**结构化回传**（不是 log，是新入站 type `renderReport`），Dart 侧在合成调试页断言「期望渲染 N 段、M 个 iframe、无 error」是否成立。
- 这一步让「渲染是否正确」从「肉眼看」变成「机器断言」。

### 5. 性能测量方法（给人类的真机步骤）
- 帧率：Flutter DevTools `Performance` 面板看 `Raster/UI` 帧时间；或 `flutter run --profile` 真机 + `flutter drive` 录 traces。
- 内存：DevTools `Memory` 面板，看 RS Image/page。
- iframe 数量 / DOM 节点数：**已有** `[WV-5] cardIframes=` / `groups=` / `nodes=` 日志，直接 grep 日志计数即可（可观测性已就绪）。
- 步骤建议：进入百条聊天 → 依次看 `[WV-5]` 日志确认 iframe/DOM 数 → 记录滚动帧率变化 → 触发一次全量重渲染观察节点重建耗时。
- **这套脚手架应排第 0 期**，因为它决定后续每一期「改完能不能本地验证」。

## B4 分期落地计划

### 第 0 期：测试脚手架（最优先，收益最确定）
- **目标**：合成消息调试页 + fixture 语料库 + 切段器/围栏/序列化的 Dart 单测骨架 + `renderReport` 回传通道。
- **改动文件**：新建 `test/`、`DiaoYan/EJS扫盘/fixtures/`；`webview_chat_stage.dart` 仅新增一个 `renderReport` 入站 type + debug 入口（**不碰渲染逻辑**）。
- **开关**：无（纯新增，回归面为零）。调试页入口仅 debug。
- **验证**：人类跑 `flutter test` 看单测通过；进调试页喂一条畸形消息看渲染。
- **回退**：删除新增文件即可。
- **风险**：极低。
- **预估轮次**：1。
- **对 7 症状**：全部「未动」（但为后续每一期的「可验证」铺路）。

### 第 1 期：故障隔离底座（不炸）
- **目标**：批量序列化兜底 + 逐条 try + 外层 catch 不抹页 + appendToken 不清块 + prepend 倒序 + 围栏保护（折中版）。
- **改动文件**：`webview_chat_stage.dart`（`_serializeMessage`/`_pushMessages`/shell 内 `setMessages`/`appendToken`）+ `chat_bridge.dart`（U+2028 注入自检）。
- **开关**：`FeatureFlags.wvErrorIsolation`（默认 false；本期上线后置 true 灰度）。老路径（无 try、抹页）完整保留在 false 分支。
- **验证**：人类在真实聊天里复现「百条 + 重前端」→ grep `[WV-8]` 确认单条失败只降级不中断；grep `[WV-8] BATCH-FAIL kept-rendered` 确认不再抹页。
- **回退**：开关切回 false，即回老路径。
- **风险**：中（动了 shell 核心，但开关可切）。
- **预估轮次**：2。
- **对 7 症状**：6 解决；5 解决；3 缓解；2 缓解（倒序）；1/4/7 未动。

### 第 2 期：定向 diff + DOM 窗口化（不卡、能看全）
- **目标**：append/prepend/update/remove 四原语 + 全量重建 fallback + 视口 ±3 窗口化。
- **改动文件**：`webview_chat_stage.dart`（`_pushMessages` 触发账本改为 diff 判定）+ shell（新增四个 handler + 窗口化）。
- **开关**：`FeatureFlags.wvDiffUpdate`、`FeatureFlags.wvWindow`（默认 false）。
- **验证**：人类在调试页喂百条，观察 `[WV-5]` 节点数不再随全量重建暴涨；grep DIFF-MISMATCH 确认 fallback 生效；滚动观察帧率。
- **回退**：双开关切 false，回到全量重建老路径。
- **风险**：高（新建 diff 引擎，状态双持需收敛）。**必须由第 0 期 renderReport 断言兜底。**
- **预估轮次**：3。
- **对 7 症状**：1 缓解；2 解决；6 保持解决；3/4/5/7 未动。

### 第 3 期：同消息多前端（能力）
- **目标**：切段器 + 消息级 iframe（整条一个 iframe 承载所有 HTML 段，文本段不进 iframe）。
- **改动文件**：`webview_chat_stage.dart`（切段器纯函数 + 序列化 + shell 消息级 iframe）+ 新增单测。
- **开关**：`FeatureFlags.wvMultiFrontend`（默认 false，务必独立开关）。
- **验证**：第 0 期调试页喂「播放器 + 点击回复 + 状态栏」多前端 fixture，`renderReport` 断言 iframe=1、段=3、无 error。
- **回退**：开关切 false，回到单 body 路径（`segs` 字段兼容回滚，保留旧 `html` 通道）。
- **风险**：高（就是方案α翻车的领域，但这次有第 0 期断言 + 阶段1兜底 + 开关）。
- **预估轮次**：3~4。
- **对 7 症状**：4 解决；7 解决；1 缓解；3/5/6 保持解决；2 保持解决。

### 第 4 期：原生兜底层（底线）
- **目标**：Flutter 原生纯文本列表 + 自动/手动降级提示。
- **改动文件**：新增一个 native ListView widget；`webview_chat_stage.dart` 加崩溃自愈超限后自动切 native、手动切换入口。
- **开关**：`FeatureFlags.wvNativeFallback`（默认 false）。
- **验证**：真机触发 WV-6 崩溃连续 3 次，确认自动降级到可读可滚可复制文本。
- **回退**：切回 false，即无兜底层（回到自愈reload）。
- **风险**：低（纯新增，独立渲染路径）。
- **预估轮次**：1~2。
- **对 7 症状**：1 缓解（最坏仍有正文可读）；其余保持。

## B5 风险登记表

| 风险 | 触发条件 | 影响 | 预防 | 发生后怎么退 |
|---|---|---|---|---|
| 引擎房被破坏 | 改 shell 骨架 / reload 序列 / `_inject*` 或 `createEngineRoom` | 变量/EJS/MVU 全废 | 约定：引擎房挂 `#root` 外，改造只动 `#root`；不碰 `__engineRoomHost` | 恢复 `_inject*`+`createEngineRoom`；或回退 shell 改动 |
| EJS 提示词侧被影响 | 动 `bundle/stub/mvu` 注入或 `__emitToEngine` | 提示词组装崩 | 本轮所有改造不碰注入链（铁律） | 回退对应 commit |
| 性能反而变差 | diff 引擎 bug 导致高频重建；窗口化 N 太小 | 卡顿 | diff 用 renderReport 断言 + DIFF-MISMATCH fallback；N 真机实测 | 开关切回全量重建 |

## B6 明确回答的问题清单

### 1. 混合/兜底架构在「单 webview」硬约束下可行吗？
**可行。** 兜底层是 Flutter 原生列表，与 webview **不同时工作**（只在崩溃自愈超限时切过去），不产生多 webview 性能叠加。隔离单位始终是同一个 webview 内的 iframe。

### 2. `_htmlShell` 抽成 asset 文件值得做吗？哪一期？
**值得，排第 2 期（或第 0 期做完脚手架后顺手）。** 收益是可静态发现语法错误 + 行号稳定 + 告别三层转义；代价是打包配置 + 动态插值改造。**优先级低于第 1 期**（先不炸，再重构）。

### 3. 测试脚手架先做还是边做边补？
**先做（第 0 期）。** 上一轮失败的本质就是没有本地验证手段；脚手架把反馈闭环缩短到「改完立刻知道」，是后续每一期「可验证」的前提。

### 4. `backup/c1-alpha-failed` 里哪些可以捡回来复用？
- **T1（ed53b33）整体捡回**：单条隔离 + 外层 catch 不抹页 + prepend 倒序。
- **T4（03795b9）捡回**：appendToken 不清块 + setImage 幂等（需补 reroll 防残留）。
- **T5（9beb998）捡回**：自愈上限 3 次。
- **T3（1ed9490）捡思路**：围栏保护，但占位符实现要改（防占位符被正则破坏），且建议折中「只保护围栏、不封死正则改卡片」。
- **T2（4ad4097）舍弃**：方案错 + 实现放大祸根（每条消息都变 iframe + 批量序列化未兜底）。

### 5. 有没有「必须先做否则后面全白做」的前置项？
**有，两个：**
- ① **循环前失败面兜底 + 可观测日志（第 1 期核心）**：不解决，任何后续改动仍会「全灭且无日志」，重蹈 α 覆辙。
- ② **测试脚手架（第 0 期）**：不解决，后续每一期都只能真机手测，反馈慢、炸了才知道。
这两个是「地基」，其余都是「上层建筑」。

### 6. 如果只能做一期就停手，做哪一期收益最大？
**做第 1 期（故障隔离底座）——但建议带上第 0 期的最小验证手段。**
理由：第 1 期直接对症状 6/5/3 三个「用户每天都在痛」的 bug 生效，收益最确定；且它建立「逐条隔离 + 不抹页」的正确骨架，让后续所有改动有了「不炸」的安全网。第 0 期虽收益最大（决定长期可验证性），但只做它用户感知不到变化，所以「只做一期」的交付以第 1 期为准，第 0 期作为它的前置小步并入。
