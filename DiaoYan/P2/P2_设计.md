# P2 设计 — diff 渲染 + 视口窗口化(零改动,纯文档)

> 现状锚点:shell 里 `setMessages`(assets/chat/chat_stage.html:1028)是全量重建;虚拟化(914–968)只对 card iframe 做视口外 `about:blank`/滚回恢复。
> 本文将两件事出设计,不动代码。

## 一、现状(供设计依据的锚点)

1. **全量重建**:`setMessages` 里 `options.initial` 时 `root.innerHTML = ''`(1041)清空整页,再逐条 append;非 initial 走 append/prepend 分支(1131–1135)。没有按 id diff。
2. **card iframe**:`if (isRichHtml(m.html))`(1087)才 `document.createElement('iframe')` 建卡,`data-frame-id = m.id`(1095),`data-html = m.html`(1096)。卡片脚本状态由 iframe 内部维护,重建 iframe 会丢状态。
3. **楼层标记**:`wrap.setAttribute('data-floor', m.floor || 0)`(1122),`scrollToFloor` 用 `[data-floor=...]` 定位(1198)。
4. **滚动**:`scrollToBottomWhenStable`(1227)靠 `lastElementChild.scrollIntoView`(1236);`__stickBottom`(1265) + `__programScroll`(1266)区分程序滚动/用户滚动。
5. **虚拟化现状**(914–968):已有一个 IntersectionObserver,屏幕外 iframe 清 `srcdoc`、滚回按 `data-last-height` 恢复。它**只处理 card iframe**,不处理整层 DOM。

## 二、diff 渲染设计

### 目标
`setMessages` 收到一批消息后,不再 `innerHTML=''` 全清,而是按消息 id 对已有 DOM 做增量增删改。

### 方案(按 id diff,三段走)

1. **建立索引**:每条消息组 DOM 根用 `data-msg-group-id = m.id` 标记(现在只有 `.msg[data-id]` 在 wrap 上,group 层没 id 锚点,需要**给 group 层补一个稳定锚**——这是唯一需要在渲染层新增的属性,不改渲染路径判。
2. **关键前提——卡片状态保持**:
   - **绝不能对"内容未变的消息"重建 iframe**。判定依据:`m.html` 与已渲染节点的 `data-html` 是否逐字相等。
   - **同 id 且 html 不变**:跳过整条(group 原样留着),**card iframe 不碰**,脚本状态保留。
   - **同 id 但 html 变**(如 reroll 后同 id 换了内容):这是少数,才删旧 group 重建。这里 iframe 状态的丢失是**语义正确**的(内容真变了),可接受。
   - **新 id**:append(或按 prepend 逻辑插头)。
   - **消失的 id**:删掉对应 group。
3. **手势/顺序**:append 走 `appendChild`,prepend 走 `insertBefore(firstChild)`(沿用现有 1131–1135 的分支),diff 只决定"增/删/改",不改变插入位置语义。
4. **楼层/版本条**:`buildFloorTag`/`buildSwipeBar` 是纯展示、随 group 重建,无需单独 diff;但 `data-floor` 若可按 id 复用旧值,则连 group 一起复用即可。

### 必须说明的"如何不破坏已有 card iframe"

- 通过 `data-html` 逐字比对:只要 `m.html` 没变,`data-html` 没变 → 该 group(连同其 card iframe)**完全不触碰**,iframe 内部脚本状态、滚动位置、`localStorage` 覆盖、事件监听都不受影响。
- 隐患与对策:
  - **隐患 1**:`innerHTML=''` 全清是现在的隐式"重置",diff 后要确保 initial(全量刷新)语义仍走全清——即 diff 只对 **append/prepend/部分更新** 生效,`options.initial` 仍全清重建(保留现有行为)。
  - **隐患 2**:`m.html` 相同时如果渲染依赖外部状态(如 `window.__avatars` 变了要重刷头像),diff 会漏更新。对策:引入版本号或把头像/名字也纳入比对键。
  - **隐患 3**:卡片 iframe 内容相同但 `injectBridge` 依赖的 libs/macros 变了(如角色切换),diff 会漏。对策:角色/会话切换时强制走一次 initial 全清(在 Dart 侧以 `initial:true` 触发,已是既有通道)。

- **与虚拟化的关系**:diff 本身不处理视口,虚拟化(第二节)是另一层;两者叠加时,diff 保证"滚回来的内容是对的",虚拟化保证"视口外的 DOM 被摘除以减少总节点"。

## 三、视口窗口化设计

### 目标
`nodes=34263 / groups=350` 线性增长,把视口外的楼层 DOM 摘除、滚回来重建,控制总节点数。

### 方案(楼层级摘除 + 重建)

1. **摘除粒度 = 楼层(group)**,不是单条消息、不是整页。这样滚动连续、重建成本可控。
2. **摘除动作**:视口外(加上下缓冲区若干屏,如 ±1~2 屏)的 group,用 `root.removeChild` 摘除,并**把它序列化进一个离屏缓存**(内存里的 Map<floor, HTML 字符串>),不写盘。
3. **重建动作**:滚回到缓冲区内时,从缓存取回 HTML,`insertBefore` 回正确位置。
4. **保持滚动位置不跳(核心难点,方案如下)**:
   - 摘除一个视口上方的 group 会**把后续内容往上顶**,导致视口内容上移。对策:**用占位符保高**——摘除时在该楼层位置插入一个**等高的空占位 div**(`style.height = 该 group 的 offsetHeight`),缓存的真实内容滚回时再替换占位符。这样摘除不改变文档总高度,滚动位置不跳。
   - 下方楼层摘除同理:占位符保留高度,滚下去时换回真内容。
   - 占位符高度需要动态维护:卡片 iframe 加载会变高(现有 `data-last-height` 机制 767/925/944 已记录卡片真实高度),窗口化应复用这个高度作为占位高度,并用 ResizeObserver 更新。
5. **与 card iframe 虚拟化的关系**:现有虚拟化(914–968)已经对"视口外的 card iframe"做了 `about:blank` 摘除。窗口化是更大粒度(整层 DOM)。两者可分层:窗口化只管 group 层,group 内部是否含 iframe、iframe 是否被虚拟化,互不干扰;但要避免**双摘除冲突**(一层已在摘 DOM,一层在摘 iframe)。设计上建议:窗口化做 group 摘除时,顺带把内含 iframe 一并摘除(交给窗口化统一管),现有的 iframe 级虚拟化作为组内已重建但仍在视口内的次级手段保留。
6. **数据来源**:窗口化需要"离线内容",最干净是保留原始 `m` 数据(已解码的数组)在 JS 侧一个 Map<floor/id, 原始 map>,重建时重新跑一次「单条 DOM 构建」逻辑(复用 setMessages 里逐条建 DOM 的那段)。这要求把"单条建 DOM"抽成一个可复用函数(现在内联在循环里 1044–1136)。

## 四、diff 与窗口化的冲突点(必须先说清)

- **diff 假设"DOM 全在"**,窗口化假设"视口外的 DOM 不在"。两者叠加时,diff 的"比对新旧"会把"被窗口化摘除的节点"误判为"该删除的消息"。
- **解决**:diff 只在**缓存数据层**做(对原始 m 数组按 id diff),DOM 层只负责"把 diff 结果应用到当前视口内 + 更新缓存"。即:**确定 diff 动作(增/删/改)在内存数组上完成,窗口化只负责"当下哪些要在 DOM 里"**。两者以"缓存数组 = 唯一真相,DOM = 缓存的可视窗口"对齐。
- 这套改动的复杂度高,建议 P2 先落地 **diff**(收益明确:修 reroll/追加不再抖、卡片不重建),窗口化作为 P2 第二阶段、且需真机 performance 数据佐证(现 nodes=34263 是否真造成卡顿,需先量化)。

## 五、我没能验证的部分

1. **nodes/groups 数值与卡顿的因果关系**:`nodes=34263` 是引用真机日志数字,是否真造成可感卡顿需要真机 profile,静态无法定。故窗口化的紧迫性未坐实,建议先测再排期。
2. **diff 的"同 id 同 html 跳过"能否稳定覆盖所有更新场景**:头像/名字/角色切换/reasoning 变化等键如何并入比对,需真机场景枚举,未穷尽。
3. **占位保高 + 滚动不跳**:占位 div 等高的做法在卡片异步变高时的动态更新,需要真机滚动测试验证,静态只能出方向。
4. **虚拟化与窗口化双摘除的边界**:现有 914–968 的 iframe 虚拟化与我设计的 group 窗口化如何合并而不互相打架,未用真机验证,只给了"统一到窗口化管"的建议。
