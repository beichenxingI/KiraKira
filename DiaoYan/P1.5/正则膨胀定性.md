# P1.5 — 正则膨胀定性(零改动,纯文档)

> 实测背景:`[WV-2] raw=59125 afterRegex=98373`,正则处理后内容膨胀约 66%(98373/59125 ≈ 1.664)。
> 本文只读代码定性,不动任何文件。

---

## 一、正则应用链路(锚点)

1. 入口:`_serializeMessage`(`lib/presentation/screens/chat/webview_chat_stage.dart`)第一步就对 `m.content` 调 `RegexService.getRegexedString(...)`(第 2791 行),结果 `rawContent` 继续走围栏/HTML 分流。
2. `RegexService.getRegexedString`(`lib/domain/services/regex_service.dart:145`):先按 `order` 排序、过滤 disabled/placement/深度,再逐个调 `runRegexScript`。
3. `runRegexScript`(`regex_service.dart:78`):核心是

   ```dart
   return input.replaceAllMapped(regex, (match) {
     String replacement = script.replaceString;
     replacement = replacement.replaceAll(RegExp(r'\{\{match\}\}', caseSensitive: false), match.group(0) ?? '');
     for (int i = 0; i <= match.groupCount; i++) {
       final filteredGroup = _filterString(match.group(i) ?? '', script.trimStrings);
       replacement = replacement.replaceAll('\$$i', filteredGroup);
     }
     // 还有 $<name> 命名组、_substituteMacros 等
     return replacement;
   });
   ```

即:`findRegex` 匹配到的每个片段 → 替换成 `replaceString` 模板(其中 `{{match}}`/`$0` 会原样把整段匹配塞回,再叠加前后追加文本)。

## 二、三个必答

### 1. 膨胀是哪条正则造成的?能否静态定位?

**不能从代码静态定位到具体哪一条。** 原因:

- 正则脚本(`RegexScript.findRegex` / `replaceString`)是**运行时数据**(存在数据库/角色卡/世界书里),不是源码常量;`regex_service.dart` 只定义"如何应用",不含"应用什么"。
- 膨胀的机械机制是确定的:凡是 `replaceString` 里含 `{{match}}`/`$0` 的替换,且 `findRegex` 命中 **短片段** 时,输出 = 模板骨架 + 原片段,天然比输入长。例如「把 `(` 替换成 `<span>（$0）</span>`」这类会把每个括号原地扩成带 span 的长文本。
- 66% 是**运行时观测值**(真机日志),我拿不到那份具体脚本清单,无法指出是第几条、叫什么名。

**能给的结论**:膨胀 = 若干条 `replaceString` 含 `{{match}}`(或 `$0`)+ 命中频次高的正则叠加所致,是正则替换机制的**固有放大效应**,不是 bug;具体罪魁需运行时 dump 脚本列表才能点名(那一步属取证,不在本轮)。

### 2. 是否可能撑破 ```` ```html ```` 围栏 → 导致 rich 判定失败?

**可能,且这是一个真实风险,但当前代码里围栏在正则之后才处理,存在时序耦合:**

- `_serializeMessage` 顺序(webview_chat_stage.dart):先 `getRegexedString(m.content)`(2789)→ 再处理 codeBlock 围栏(2808 的 `^```[a-zA-Z]*\n([\s\S]*?)```\s*$`)与 htmlFence(2819 的 ```` ```html ... ``` ````)。
- 若正则的 `findRegex` 匹配范围横跨或伸入 ```` ``` ```` 围栏内部,并把围栏起始/结束标记(```)本身或围栏里的内容替换成别的文本,就会打破「围栏成对」结构 → 后续 `htmlFenceMatch` 的正则 ````` ```html\s*\n([\s\S]*?)``` ```` 匹配不到 → 该卡不走 `iframe` 渲染,降级为 Markdown 文本块。这与 `raw=59125→98373` 膨胀同方向(文本被正则改写后,结构化标记更易被破坏)。
- 但要注意:膨胀本身(内容变长)**不直接**破坏围栏,破坏围栏的是正则**恰好命中围栏标记或围栏内文本**。两者相关但非同一件事。当前代码**没有**"在正则前先把 ```` ```html ```` 围栏摘出保护"的逻辑(α 分支曾做过 C1-T3 围栏保护,但基线 34597ca 之后未保留这条),所以风险敞口存在。

**结论:可能。** 锚点:`_serializeMessage` 里 getRegexedString 先于 htmlFence 处理,围栏无前置保护。

### 3. 若要"只对围栏外的段落生效",最小改动长什么样?(只出方案,不施工)

**方案(锚点级别,不落地):**

在 `_serializeMessage`(webview_chat_stage.dart)里,把 `getRegexedString(m.content)` 移到「围栏分段」之前已经不是当前结构;当前结构是无分段直接对全文正则。最小改法是:

1. 在调 `getRegexedString` **之前**,先用 `RegExp(r'```[\s\S]*?```')` 把整段 ```` ``` ```` 围栏摘出、用占位符(如 `\u0001FENCE0\u0001`)替换,并记录原文。
2. 对"摘除围栏后"的正文跑 `getRegexedString`(正则不再能碰到围栏标记/内容)。
3. 跑完后把占位符**还原**回围栏原文。

这等价于 α 分支 C1-T3 的「围栏保护」思路,锚点是 webview_chat_stage.dart 的 `_serializeMessage` 里 `getRegexedString` 调用处(2789)。改动范围:约 10 行(摘出 + 还原),不改正则服务、不改渲染分流、不引入 `segs`。

但要**额外确认**一个前提:围栏摘出对"正则语义"的影响——若用户确实想用正则改写围栏**内**文本,此改法会使其对围栏失效。因此这不是无脑安全改动,需要产品层确认「正则是否允许作用于围栏内」。**仅出方案,不施工。**
